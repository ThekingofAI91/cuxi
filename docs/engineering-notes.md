## 一、检索：三次推演

### 1.1 查询改写（Multi-Query + HyDE）：删掉，装回来，又删掉

**实现**：一次 LLM 调用生成 2 个查询变体和 1 篇 HyDE 假设文档。变体走向量与 BM25 两路，HyDE 只走向量（长文档进 BM25 会冲淡专有名词的精确命中）。HyDE 不写入向量库，只作为查询向量使用。

**第一轮判断（2026-10-18）**：做了三轮「剂量实验」，只改首字愿意为改写等待的预算——

| 等待预算 | 改写实际生效比例 | 与关闭改写的四维差值 |
|---|---|---|
| 2s | 0%（一次 LLM 往返 3.5s 以上） | — |
| 4s | 白天 23% / 夜间 1.4% | +0.01 / +0.12 / -0.03 / +0.02 |
| 8s | 93% | +0.36 / +0.45 / -0.17 / +0.32（换了更严的判官版本，只与自身基线比） |

结论是「提升不稳定且不划算」，于是把实现、四个配置项、测试文件一起删掉（484 行）。

**推翻（2026-10-19）**：做别的改动时发现融合层有计票错误。旧实现是**扁平累加**——7 条榜不分通道一律相加。改写只在向量侧加榜（3 条），BM25 只加 2 条，于是「打开改写」这个动作顺手把向量 : BM25 的票数比从 1:1 改成了 4:3，语义路被放大 33%。**那三轮实验里「改写」和「配比变化」是两个变量**，结论不成立。

**修法**：融合改为「每类一票 + 类间权重」。`fuse_by_class` 先把同一类（vector / bm25）下的多条榜按文档取最好名次合成一票，再乘类权重与来源权重。真链路验证（阿德勒 699 条语料，2 变体 + 1 HyDE）：

- 36 个文档被同类多榜命中，压成一票后单条分数下降 47.8% ~ 66.7%；
- 新旧 top-8 只重合 6/8。

所以这不是等价重构，它确实改了排序。

**最终状态（2026-10-22）：已删除**。实现（`generate_query_variants_and_hyde` / `_rewrite_with_budget` / 语义缓存与后台补缓存）、四个配置项、`tests/test_rewrite_budget.py` 与两处调用点一并移除，`advanced_retrieval` 的 `llm` 参数随之删除。

删除理由不是「收益为负」——这个结论从未被证明。理由是：它始终没被证明为正，且一直默认关闭、生产从未启用，留着只让「代码能力」与「默认配置」不一致；要重新评估，前提是先把「关掉改写」当基线跑出可比数据（见 README 评测章节的缺对照组问题）。上一条「恢复」的判断仍然成立：10-18 那批实验混了变量，不能用它给改写定罪。

### 1.2 精排候选池必须大于注入条数

早期 `candidate_limit` 等于注入条数（两者都是 8）。这意味着 Cross-Encoder 无论怎么排，都改不了「哪几条进 prompt」，只在改顺序。

2026-10-18 做「精排输入视野 200 字 vs 500 字」的全量实验时，110 题五维全部落在噪声层内（忠实 9.13 → 9.16、相关 9.83 → 9.77、精确 8.22 → 8.20、覆盖 9.61 → 9.63、口吻 8.74 → 8.81，31/109 题总分完全没变），成本却确定增加 0.6s/题。原因是判官读的是全部注入块，对块内顺序不敏感；而集合又根本没变。

**改法**：拆成 `rerank_pool_size=10`（候选池）与注入条数两个概念。池子 10 条整池精排后取前 5，10 对约 1.9s（单对约 190ms）。

**2026-10-20 的后续（当前形态）**：整池精排又往前走了一步。40 题探针显示「RRF 前五」与「精排后前五」的交集均值只有 2.80/5，而被踢掉的常常正是 RRF 第 1 名——那是原文出处段，单独一段读起来反而偏题，但它是回答的锚。于是改成两段式：池内前 3 条按 RRF 名次直通（`rerank_anchor_k=3`），剩下 3 条从尾部 7 条里精排选出，注入 6 条，7 对约 1.3s。这一步把上面的结论推得更远一层：精排该用在名次密集、RRF 分数差很小的尾部，而不是替融合结果重新投票。

**代价**：精排从「排座」变成「选人」之后，之前那些「换模型 / 改视野，进 prompt 的集合 24/24 一致」的 A/B 结论全部失去前提，需要重测。这是一次典型的「结论必须绑定当时的架构口径」。

### 1.3 精排视野 500 字与模型硬上限

`bge-reranker-base` 的 `max_position_embeddings` 是 514。实测「1000 字 + `max_length=1024`」与「+512」的分数逐位相同——超出部分直接被位置编码截掉，全文精排在这套模型上做不到。

200 字 vs 500 字的排序差异（98 题 × 8 候选 = 784 对）：

| 指标 | 数值 |
|---|---|
| top1 一致 | 44.9%（44/98） |
| top3 完全相同 | 24.5% |
| Jaccard | 0.568 |
| Spearman | 0.636 |

按块长分组：≥800 字的块平均 +0.123 logit，<300 字的块 -0.017。说明长块的答案信息确实落在 200 字之后。因此视野定在 500 字 / 512 token。

### 1.4 RRF 为什么按类计票

公式 `class_weight × source_weight / (rrf_k + rank + 1)`，`rrf_k=60`，`rank` 从 0 起。榜内的向量距离与 BM25 分数只用来定名次，不进公式——两者量纲不可比（余弦相似度封顶 1.0，BM25 无上界）。

来源权重按文档的语料类型给，每类乘一次：anchor 2.0 / oral 1.5 / original 1.2 / artificial 0.6 / secondary 0.25。目的有两个：让「学说话方式」优先拿到口述语料；把「别人评价这个人」的二手解读压下去，防止第三者观点冒充原话。

代价要写清：阿德勒最流行的表述（目的论、课题分离、共同体感觉）出自《被讨厌的勇气》，该书作为后人转述被 0.25 强降权，问这些概念时原书表述可能召不回来。这是「防冒充」与「概念覆盖」之间的真实权衡，目前没有解掉。

## 二、分块与入库

### 2.1 碎片重组（2026-08-13）

扫描版 PDF 的 OCR 输出是逐行碎片，平均 40–60 字符。按原文顺序拼接、去重后重新分块，该库块数从 188,661 降到 4,965（-97.4%），BM25 磁盘缓存与内存占用同步下降，检索质量反而提升。

此后 chunk 参数、去重规则、前置页过滤又各改过一轮，各库分别重建。当前合计 5,701 块（荣格 2,988 / 王阳明 1,269 / 阿德勒 1,192 / 张雪峰 161 / 峰哥 90）。

### 2.2 块的实际长度不是 1000

`chunker` 的 `max_size = chunk_size = 1000`，但：

- `_add_overlap` 在块**首部**追加 100 字重叠 → 实际 1000~1100；
- `_merge_short_tail` 刻意不卡 `max_size`（冲突时下限优先），最长可到 `max+min-1 = 1499`。

全量审计：荣格 96.2% 的块超过 1000 字（中位 1158），王阳明 99.5%。

**这意味着注入侧的 `[:1000]` 不是保险丝，而是常规操作。**它砍的是块尾（较新的内容），留下的是块首那 100 字重复重叠，还把分块器已经切好的句子边界破坏一次。块尾落在句末标点的比例：

| collection | 原始块 | 被 `[:1000]` 截断后 |
|---|---|---|
| 荣格 | 18.3% | 6.6% |
| 王阳明 | 44.2% | 5.3% |
| 阿德勒 | 59.7% | 46.5% |
| 峰哥 | 22.2% | 14.4% |
| 张雪峰 | 42.2% | 42.2%（仅 1 块超 1000） |

**10-19 的改法**：`inject_doc_chars=1500` + `_clip_at_sentence()`——超上限时往回收缩到最近的句号/问号/分号/换行，找不到像样边界且截掉超过半个窗口才硬切。1500 覆盖全库 99.9% 的块（5,700 块里只有阿德勒 4 块、峰哥 1 块超过），实际等于没切。

**10-20 把上限整个删掉**：既然 99.9% 的块都碰不到它，这道限制只剩一个副作用——让「注入的是不是原文全文」变成需要额外解释的事。`inject_doc_chars` 与 `_clip_at_sentence` 一并删除，注入就是块原文；注入总量由「条数 × 块长」决定，不存在 7.5K 这类封顶（那只是 5×1500 的算术，不是任何环节的预算）。

### 2.3 块尾断裂的根因在解析层

荣格原始块只有 18.3% 结尾是句末标点，说明 OCR 把任意换行当成了段落边界，段落本身就断在句中——`chunk_size` 只是把这些碎片装进一口 1000 字的袋子。

要根治得改 parser 或改成按页切分（`parser.py` 已经产出 `page_num`，是 chunker 没透传；荣格约 0.65 块/页、约 750 字/页）。但按页切会把块数抬到约 4,600，且 chunk 一变就必须重建 collection 与知识图谱，而建图是逐块 LLM 抽取、受网关速率限制。目前没做。

### 2.4 前置页过滤

**动机**：一道「原型和集体潜意识是什么关系」的题，`[1]` 号原文是《原型与集体无意识》的书名页 + 版权页混编块——通篇译者、出版社、统筹监制。它命中的原因很直白：书名页把两个关键词各重复四五遍，向量与 BM25 都判它最相关。这是典型的标题堆砌型 hard negative。

**判据经过三次修正**：

1. 「≥2 类痕迹即判前置页」→ 误伤正文段落（正文里也可能提到出版信息）。收紧为强标记命中（ISBN / 图书在版编目 / CIP / 出版发行 / 版权所有）。
2. 收紧后仍漏掉没 ISBN 的封面页（ISBN 在另一页）。补「职务栏用词 ≥2 个」（统筹监制 / 特约编辑 / 市场推广 / 珍藏版…）。
3. 「整块丢还是只删几行」：加句读密度（每 100 字的句末标点数，正文 2~5、版权页 0~0.5）。起因是《阴影与自我》有一块 1,193 字，前面是荣格生平、末尾粘了版权页——按类型整块丢会把传记一起丢掉。

实现在 `src/retrieval/corpus_filter.py`，接在向量化**之前**（清洗会改文本，先清洗再 embed 才能保证向量与文本一致）；上传路径同样处理，全部被滤时返回 400。共删除 8 块、清洗 4 块。

**在条数上是小头（8/5,706），在排序上是大头**——它命中的是 top1。这类占比极低但排位极高的噪声，只能靠看检索结果反推，聚合指标看不出来。

## 三、上游故障与容错（2026-08-29）

### 3.1 根因诊断

分阶段计时 + 语料扫描（脚本 `scripts/profile_rag.py`）排除了三个嫌疑人：

- **语料质量**：荣格库 2,994 块全扫，乱码块 0 个，块长中位 1,158——不是延迟原因；
- **知识图谱**：3 个角色存在空图谱文件（0 实体），荣格库有烂尾 tmp（66 chunk / 0 实体），构建每次都空手而归；
- **上游 LLM**：中转存在随机故障，**HTTP 200 但 content 为空**，约 13s 超时后返回空壳，同一 prompt 时好时坏。图谱抽取每批全空，因此 0 实体；主链路靠重试救回——这是教育区延迟在 8s 与 21s+ 之间波动的主因。
- 精排当时实测（v2-m3，CPU）5 对约 4-6s，占检索阶段 95% 耗时。

### 3.2 修法

1. **空响应检测 + 有限重试 + 首 token 超时**（`llm.ainvoke_nonempty` / `astream_nonempty`）：空壳视为失败立即重试，最多 2 次；流式版加 `llm_ttft_timeout`（默认 6s），把单次尝试代价从 13s 压到 6s。只在「未向用户推送任何 token」时重试，不会重复输出。重试耗尽后明确报错（SSE `type: 'error'`），不再静默回退成「无资料直答」——那会丢掉本轮全部检索结果。
2. **图谱抽取改行式格式**（`实体 | 关系 | 实体 | 证据`，一行一条）：绕开上游对结构化输出指令的故障模式，同时降低单批输出量。
3. **构建熔断**：连续 5 批 0 三元组即判定上游不可用，中止并清理 tmp，不白烧几百次调用。
4. **空图谱不算已存在**：`graph_exists` 要求 entities > 0，空文件自动触发重建；清掉 3 个空图谱与烂尾 tmp。
5. **构建失败退避**：失败后 1 小时内不自动重试（手动 force 不受限）。

### 3.3 精排模型的选择

实测 `bge-reranker-base` 比 `v2-m3` 快约 3.4 倍（1,400ms → 370ms 量级），体积 2.27GB → 1.1GB；24 个真实查询的检索级 A/B 里排序一致性 Kendall tau 0.908，12 题端到端得分持平。

仓库默认值取 `base`（`RERANK_MODEL` 可切回 v2-m3）。**注意**：那组 A/B 是在「候选池 = 注入条数」的前提下做的，池子放大到 10 之后「集合完全一致」这条证据需要重测，目前只保留「排序一致性」与「12 题端到端持平」两条。

## 四、并发与延迟原始数据

### 4.1 20 并发压测（2026-08-13）

条件：16 核 CPU、单进程、torch 8 线程、精排并发上限 2、精排候选 10 条、精排输入截断 200 字；20 个请求同时发起，全部走完整检索 + 生成。

| 指标 | 调优前 | 调优后 |
|---|---|---|
| 20 并发总耗时 | 191s | 109s |
| 单请求最短 / 最长 | 45s / 191s | 21s / 109s |
| 成功率 | 20/20 | 20/20 |

同批还测了「纯 LLM 20 并发」为 8.4s，说明上游 API 不是瓶颈，CPU 精排是。**这是本地压测，不是容量承诺**；此后精排视野放宽到 500 字、候选池改为 10 条，延迟未重新测。

### 4.2 精排耗时矩阵（15 组合实测）

| 配置 | 单次耗时 |
|---|---|
| 4 线程 / 15 候选 / 300 字 | 29.0s |
| 8 线程 / 15 候选 / 300 字 | 17.6s |
| 8 线程 / 10 候选 / 200 字 | 8.1s |
| 8 线程 / 8 候选 / 200 字 | 6.5s |

torch 线程数是全局的，为并发降到 4 会让单请求精排慢 4 倍；8 线程 × 2 并发是 16 核的平衡点。

### 4.3 当前检索耗时（2026-10-19，n=98）

| 阶段 | 均值 | 中位 |
|---|---|---|
| 文本检索（向量 + BM25 + 融合 + 精排） | 2,315.6ms | 1,895ms |
| 图谱触发判断（纯词法） | 42.7ms | 2.4ms |
| 图谱子图扩展 | 74.9ms | 18.8ms |

图谱边际成本约为文本检索的 1%~3%。

### 4.4 首字延迟的两条数据别混

- **寒暄消息**：模型判定不检索，一次 LLM 直出，首字约 2s。
- **完整链路单请求**（110 题评测记录，含检索 + 生成 + 精排）：中位 11.8s、均值 13.9s、P90 23.2s、最长 31.3s。

历史上检索端到端曾从 3.9s 优化到 2.4s（改写默认关闭 + 精排分数 LRU 缓存 2000 条），重复提问精排零推理（实测 0.05s）。此后视野放宽与候选池放大各增加约 0.5s 与 0.4s，净额约 2.0~2.4s，与上表 2.3s 一致。

## 五、前端视觉的一次重构（2026-08-29）

参照克制型暗色界面重做：中性炭灰单色底（各角色只差底色微调），每个角色一个低饱和强调色（哑铜金 / 哑陶土 / 哑青绿 / 雾蓝），仅用于极小元素；全面扁平化——去渐变、去光晕、去噪点纹理，发送按钮、气泡、输入框、徽章统一为中性面板 + 细边框；移除全部 emoji 装饰图标，选区卡与头像改名字首字徽章。

王阳明的纸墨主题未动。纸墨（`--paper/--ink/--line/--red` 一组变量）与暗色主题是两套变量，每个颜色都带 `var()` 兜底。
